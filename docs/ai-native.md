# KB × AI Native — 设计文档

> 「智能软件开发」课程作业 · `ai-native` 分支
> 从「AI 可操作的知识库」到「AI 内生的知识库」

## 一、背景与动机

KB 是一个自托管的单文件知识库（FastAPI + SQLite + 原生 JS SPA），核心数据模型非常简单：
**页面 = 名字 + Markdown 正文**，所有结构信号（双向链接、标签、属性）都从正文实时解析。

在此之前，它已经通过 **MCP（Model Context Protocol）暴露了 17 个工具**——外部 AI
Agent（CLI / 聊天端）可以搜索、读写、重命名、逐行编辑页面。这解决的是
**「AI 能不能操作这个应用」**：AI 是调用方，应用是被调用的数据源。

但这是 *AI-operable*，不是 *AI-native*。AI-native 意味着：**AI 参与应用自身的核心循环**，
用户不离开应用就获得 AI 增益，AI 的产出直接沉淀为应用的数据结构。

笔记系统的核心循环是 **写（捕获）→ 连（组织）→ 问（检索）**。
本分支把 AI 嵌进这三个环节，每个环节一个功能：

| 环节 | 功能 | AI 做什么 |
|---|---|---|
| 问 | **RAG 对话面板** | 基于你的库检索上下文回答，引用可点击跳转 |
| 写 | **编辑器划词操作** | 润色 / 续写 / 总结 / 自定义指令，结果可撤销 |
| 连 | **保存后链接建议** | 找出「提到了但没建链」的概念，一键建 `[[双向链接]]` |

其中「连」是知识库独有的 AI-native 场景：LLM 的语义理解被用来**强化双向链接图谱**——
这是通用聊天应用做不了、必须长在数据模型上的功能。

## 二、总体架构

```
┌────────────────────────── 浏览器 SPA ──────────────────────────┐
│  ✨ AI 面板(问)      划词工具条(写)      链接建议卡片(连)        │
│      │ fetch+SSE          │ fetch               │ fetch        │
└──────┼────────────────────┼─────────────────────┼──────────────┘
       ▼                    ▼                     ▼
┌───────────────────────── FastAPI /api/ai/* ────────────────────┐
│  chat(SSE流式)      edit(编辑动作)      links(建议/应用)         │
│       │                    │                     │             │
│       ▼                    │                     ▼             │
│  ai.build_chat_context     │           ai.suggest_links        │
│  (jieba分词→FTS5检索        │           (LLM提议→服务端硬校验    │
│   +当前页全文→拼上下文)      │            →apply_link安全替换)   │
└──────┼────────────────────┼─────────────────────┼──────────────┘
       ▼                    ▼                     ▼
   ┌───────────── 任意 OpenAI 兼容 LLM 服务 ─────────────┐
   │  默认智谱 GLM (glm-4-flash 免费档);可换 OpenAI 等    │
   └────────────────────────────────────────────────────┘
```

关键设计决策：

1. **无状态代理**：后端只做「检索→拼上下文→转发→校验」，不存对话、不做后台任务，
   每个请求自包含。这让三个功能都能独立测试与降级。

2. **RAG-lite 检索，不上向量库**：个人知识库规模（百级页面）下，
   `jieba 分词 → SQLite FTS5 trigram 检索 → 取 top4 + 当前页全文` 的混合检索已够用，
   且零额外基础设施。语义检索（embedding）列为展望。

3. **LLM 输出一律过服务端硬校验**（最重要的安全决策）：
   链接建议返回后，服务端逐条验证 anchor 确实逐字存在于正文、不在代码块/已有链接内、
   target 确实是库里的页面、没有重复链接；「应用」操作由服务端执行安全替换并同步
   refs 索引。**LLM 永远不直接写数据库**——它只能提交候选，规则引擎裁决。

4. **优雅降级**：不配 `KB_AI_API_KEY` 时三个功能整体禁用（顶栏按钮变灰、面板显示配置
   引导），其余功能完全不受影响。AI 是增益，不是依赖。

## 三、功能详解

### 问 · RAG 对话面板（`POST /api/ai/chat`，SSE 流式）

- 前端右抽屉聊天面板，用户消息 + 流式 AI 回复（120ms 节流的增量 markdown 渲染）。
- 服务端每轮取「最近 2 条用户消息拼接」做检索（追问"那第二点展开讲讲"也能召回原话题）：
  当前页面全文（勾选开关，最多 4000 字）+ 最近 7 天日记（勾选开关，日期名页面各 1500 字，
  ≤10 篇）+ FTS5 检索 top4 相关页（各 1200 字），拼进 system prompt。
- System prompt 要求：只依据上下文回答、没有就明说、**引用来源写成 `[[页面名]]`**。
- **引用可见化**：SSE 首帧返回本轮上下文用到的页面列表（`context_pages`），前端在气泡上方
  渲染成可点击的 chips——grounding 可审计，也是"防编造"叙事的支点。
- 前端复用应用的 markdown 渲染管线，`[[引用]]` 直接渲染成可点击的 wikilink。
- **周报生成**：预设 chip「📅 本周总结」= 自动勾日记上下文 + 预填指令 + 发送；
  每条 AI 回复带「📄 存为页面」——内联改页面名（默认 `周报-YYYY-MM-DD`）后建页。
- **对话持久化**：localStorage 保存最近 40 条（含引用页），刷新不丢，「清空」即新对话。

### 写 · 编辑器划词操作（`POST /api/ai/edit`）

- CodeMirror 里选中文字 → 浮出工具条：`✨润色 / 续写 / 总结 / ✎自定义指令`。
- 润色/自定义 = 替换选区；续写/总结 = 追加在选区后（总结转 blockquote）。
- 全部通过 CodeMirror 的 `replaceSelection` 落盘到编辑器缓冲区，
  **Ctrl+Z 一步可撤销**，不自动保存——人始终是最后一道闸门。

### 连 · 保存后链接建议（`POST /api/ai/links` + `/links/apply`）

- 保存页面成功后前端异步请求建议（按内容签名去重，不重复打扰）。
- 服务端把正文（4000 字）+ 全库页面名列表交给 LLM，要求返回
  `[{anchor, target, reason}]` JSON——anchor 必须是正文原文片段。
- 服务端硬校验（见设计决策 3）后返回；前端在页面顶部显示建议卡片，
  每条「原文片段 → 目标页面 + 理由」，可逐条**应用**或整体**忽略**。
- 应用后：正文片段变为 `[[目标页|原文片段]]`（别名语法保持原文可读），
  refs/反链/图谱即时更新，页面自动重载。

### 连+ · 全库批量扫描（`POST/GET /api/ai/links/scan`）

- 体检区「✨ AI 建链扫描」一键启动：后台任务逐页跑建议（最近改动 40 页、正文 ≥80 字），
  前端 1.5s 轮询进度，完成后按页分组展示，逐条应用/重扫。
- 存量库冷启动入口——不需要逐页保存才触发建议；应用走同一个硬校验端点。
- 状态在应用进程内存（单进程模型），重启回到 idle；同时只允许一个扫描任务。

## 四、配置

| 环境变量 | 默认 | 说明 |
|---|---|---|
| `KB_AI_API_KEY` | （空=禁用） | 任意 OpenAI 兼容平台 key |
| `KB_AI_BASE_URL` | `https://open.bigmodel.cn/api/paas/v4` | 智谱 GLM；换 OpenAI/DeepSeek 只需改这里 |
| `KB_AI_MODEL` | `glm-4-flash` | 免费档，作业演示够用 |

```yaml
# docker-compose.yml
environment:
  - KB_AI_API_KEY=your-key
  # - KB_AI_BASE_URL=https://api.openai.com/v1
  # - KB_AI_MODEL=gpt-4o-mini
```

### 无 key 测试（mock LLM）

`scripts/mock_llm_server.py` 是一个确定性的 OpenAI 兼容 mock（支持 SSE 流式），
按 system prompt 前缀路由到固定回答，用于无 key 的端到端测试：

```bash
# 容器内启动（kb-test 约定端口 8011）
docker exec -d kb-test python scripts/mock_llm_server.py
# 应用侧配置
KB_AI_BASE_URL=http://127.0.0.1:8011/v1 KB_AI_API_KEY=mock KB_AI_MODEL=mock-1
```

## 六、局限与展望

- **检索是关键词级**：jieba+FTS 召回，无语义向量。展望：SQLite 存 embedding 做混合检索。
- **每轮检索无缓存**：个人库规模下延迟可忽略；库变大可加 (query→pages) LRU。
- **链接建议的 anchor 定位**：目前取首个「自由」出现位置，同段多次出现需人工确认场景再扩展。
- **日记/周报生成**：「问」的自然延伸（按时间窗检索 + 汇总），管线现成，列为下一步。
- 与 MCP 的关系：两套接口互补——MCP 让外部 Agent 操纵库（自动化），
  /api/ai 让库内嵌智能（交互）。同一套数据模型，两种 AI 参与方式。
