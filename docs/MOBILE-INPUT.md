# 移动端输入设计

## 问题

桌面上的 vim 键位 + which-key 体验很好，但手机上：

- 没有物理键盘，`space f f` 这种序列无处可敲
- 双键连按（`dd` / `gg` / `]b`）和系统手势、输入法冲突
- 长按、`Ctrl`、`Alt` 组合基本不可用
- 状态栏的 `NORMAL / INSERT` 徽标在手机上纯属误导

结论：**移动端不该是"另一套 vim 键位"，而该是"同一批动作的另一种触发器"。**

## 做法：把「能力」和「按键」拆开

```
                 ┌──────────────────┐
                 │   ACTION_SPEC    │  一份声明式表
                 │  { lhs, ctx,     │  lhs 只是桌面按键提示
                 │    label, run }  │  run 是唯一实现
                 └────────┬─────────┘
             ┌────────────┴────────────┐
      桌面（vim 键位 + which-key）   移动（动作坞按钮）
```

这条结构直接照 which-key.nvim 的教训：**同一份 spec 同时驱动按键与帮助**，
不写第二套逻辑。桌面用 `LEADER_SPEC`（有层级前缀树，which-key 语义），
移动用 `ACTION_SPEC`（扁平 + `ctx` 过滤，按钮语义）。两者的 `run` 指向同一批函数。

`ctx` 取值：`page` / `editor` / `buffer` / `search` / `always`。
动作坞按 `ctxKind()` 过滤，所以编辑页只出现 `w p q v h s`，页面页出现 `ff sg v r x y o`。

## 三种输入模式

| 模式 | 触发条件 | 行为 |
|---|---|---|
| `vim` | 桌面（`pointer: fine`） | 纯键盘，不加任何移动端 UI |
| `touch` | 手机（`pointer: coarse`） | 动作坞 + 数字盘 + tabline 收起 + 编辑器直接可打字 |
| `auto`（默认） | 由 `(pointer: coarse)` 决定 | 平板插键盘时能自动回 vim |

运行时切换：`:vimui` / `:touchui` / `:autoinput`；调试预览：`:mobile!`。

## 移动端三个具体控件

### 1. 动作坞（右下 `＋`，点状态栏模式徽标也可）

按上下文过滤的浮动按钮组。为什么是坞而不是手势：手机上一屏能放的
可靠手势只有"纵向滚动"一种，其余都会和系统返回/侧滑/长按冲突。
按钮是一点即达，且能显示动作名（不需要背键名）。

### 2. 数字盘（`1-9`）

借用 LazyVim 给折叠/分屏编的号：数字不是随机快捷键，而是
「列表里的第 N 项」这种有意义的频次。页面上打开就是当前列表的前 9 条
（任务/页面/缓冲），点一下就跳。桌面上等价的是 `gg` + 目视扫描。

### 3. tabline 摘要条

touch 模式下 tabline 收成一行：`▤ 当前页 +N ▾`，点开显示完整列表，
右上 `▴` 收起。省下的 24px 直接给内容。

## 手势（刻意只有一条）

| 手势 | 动作 | 理由 |
|---|---|---|
| 纵向单指滑动 | 原生滚动 | 不接管，浏览器做得比我好 |
| 横向滑动 | `]b` / `[b` 切缓冲 | 与 LazyVim 的 `]b` `[b` 同义，且不与系统手势冲突 |

**wikilink 在触屏上不是长按**，是「一击预览、二击进入」：

```js
// static/app.js，click 处理里
if (isMobile() && !a.classList.contains('unresolved')) {
  if (lp.cur === a) { hideLp(); navigate('page', a.dataset.page); }
  else showLp(a);              // 第一下只弹预览
  return;
}
```

理由：长按在 Android 上是文本选择、在 iOS 上是放大镜，两个都抢事件；
而且长按没有「后悔窗口」——松手就跳走了。点两下既能看到内容摘要和
反链数，又能确认再进，是触屏上更稳的等价物。

判据是 `isMobile()`（`window.innerWidth <= 760`），不是 `isTouchUi()` ——
横屏手机、平板都算，而这个宽度判据和面板的 760px 媒体查询同一条线。

判据：`dt <= 500ms`、`|dx| >= 60px`、`|dx| >= 1.8|dy|`（`static/app.js`
的 `touchend` 里），只认"快、短、横向为主"。

## 编辑器在 touch 模式

`cm.setOption('keyMap', 'default')`，状态栏显示 `INSERT`。
手机打开编辑页就能直接打字，不需要先按 `i`。这是唯一一处
"两种模式行为不同"的地方，因为它是纯粹的输入手段差异。

## 浮层规则（触屏上最容易翻车的一类）

手机上打开的每一个浮层都必须同时满足四条，缺一条就是「有功能但用不到」：

| 规则 | 为什么 |
|---|---|
| **装不下必须能滚** | 全部浮层都向下锚定、内容向上生长；没有 `max-height` + `overflow-y:auto` 时，超出部分直接长到屏幕上方外面（`top` 变负数），等于不存在 |
| **限高用 `dvh` 覆盖 `vh`** | 软键盘弹起时 `100vh` 不变、可视区矮一半，用 vh 算出来的高度照样顶出去 —— 而「编辑时点 ＋」就是这个场景 |
| **必须有非键盘出口** | 触屏没有 Esc：遮罩点击 / × 按钮 / `closest('.ng-sheet')` 判定的空白区点击，至少有一个 |
| **打开时锁背景滚动** | `body.ng-open { overflow: hidden }`，否则遮罩上滑动会滚到下面的正文 |

已经踩过的三处（都修了，都有 e2e 守着）：

```
#fxdock    12 条动作 523px   320×568 top=-55px(1 条点不到)
                             844×390 top=-233px(5 条)  740×360 top=-263px(6 条)
#whichkey  28 条动作 758px   900×420 top=-372px(13 条)  800×340 top=-452px(16 条)
#numgrid   9 格（不超高）    但 z-index 70 被目录面板的 90 盖住 → tap 超时
```

层级现在固定成一条：

```
触屏入口(96/97)  >  KBPanel overlay(90)  >  scrim(89)  >  dock(40)  >  正文
```

**同一锚定形状的浮层已经三遍出问题**（`#fxdock` 的 z-index → `#numgrid` 的
z-index → `#whichkey` 的裁切）。新增浮层时先 grep 一遍所有
`position: absolute` + `bottom:` 的兄弟节点。

## 未做的事（以及为什么）

- **不做移动端专属快捷键表**：会分裂成两套需要同步维护的逻辑
- **不做双击/三击手势**：和系统双击缩放、文本选择冲突
- **不做虚拟方向键**：占用屏幕且体验差，不如直接滚动
- **不把 `:` 命令行搬到移动端**：手机软键盘上冒号要切两次，动作坞更快
